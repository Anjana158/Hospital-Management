This document lists what the project implements today. It is an inventory of screens, APIs, and stored records. It is not a go-live certificate and it does not report measured performance.

1. What the system is

The project is a hospital operations application for outpatient registration, daily department tokens, scheme discounts, service billing, and activity reports. Staff sign in on a shared React application. The selected role decides which area opens. The API checks that same role on every protected request.

Three working areas are present:

  • Admin maintains users, schemes, departments, the billing service catalog, and hospital-wide reports.
  • Reception registers patients, books the day’s outpatient visit, prints the OP ticket, and views that receptionist’s own statistics.
  • Billing finds or registers a patient, raises a service bill, records Cash or GPay, reprints the receipt, and reviews collection reports.

A doctor consultation module is not part of the current application. Earlier doctor records were removed from the database schema. There is no inpatient, ward, pharmacy, laboratory, inventory, or appointment-calendar module.

3. Sign-in and roles

Implemented and used by every module:

  • Login with username, password, and a selected role.
  • A user may hold more than one role. The role chosen at login is the only role for that session.
  • Passwords are stored as bcrypt hashes.
  • Five failed passwords lock the account until an administrator changes the status.
  • Account statuses are Active, Inactive, and Locked.
  • Logout revokes the refresh token.
  • The client refreshes the access token shortly before it expires.

The role names used by the routes are ADMIN, RECEPTION, and BILLING.

5. Reception module

Path: /reception. Only the Reception role can open it.

Patient registration and search

  • Register a patient with name, gender, date of birth or age, optional phone and alternate phone, address, and an optional scheme.
  • If only age is entered, the system stores 1 January of the calculated birth year and keeps the entered age.
  • If a scheme is selected, the server checks gender and age eligibility and any extra scheme fields.
  • A UHID is generated in the form UHID-YYYYMMDD- plus a random code. The value is unique.
  • Search by UHID, name, or phone, with gender and age-band filters. Results are paged, up to 50 rows.
  • Today’s newly registered patients are listed separately, also paged.
  • Open a patient, edit the record, and see that patient’s OP visits.
  • If the phone matches an existing patient, registration stops and the possible matches are shown. A patient can still be saved with no phone number.

Outpatient visit and token

  • Choose an active department and register today’s OP visit for a patient.
  • The first visit to that department is stored as New. A later visit is stored as Revisit, with a revisit count.
  • The screen blocks a second visit when the patient already has a non-cancelled visit in that department today.
  • Each department has its own daily token series. The token label is HMS followed by the number. The counter is updated in one database statement so two desks do not receive the same number.
  • The visit number looks like OP-YYYYMMDD-000123.
  • Scheme discount is calculated on the server from the patient’s active scheme and stored on the visit, together with the scheme name and eligibility as they were at that moment.
  • The payable amount is recorded as Cash, GPay, or Free when the amount after discount is zero.
  • Today’s OP list is paged. An OP ticket can be opened again later for reprint.

Reception reports

A receptionist can run a personal report for a day, week, month, or custom range. It counts that person’s visits by department, gender, age band, and new versus revisit, and it totals the OP amount collected in Cash and GPay.

6. Billing module

Path: /billing. Billing staff and administrators can open it.

  • Search an existing active patient by UHID, name, or phone.
  • Register a new patient from the billing screen, using the same registration rules as reception.
  • Add one or more catalog services, set a quantity, and choose APL or BPL. The price comes from the current tariff, not from a typed amount.
  • Request a quote before saving. The server validates scheme eligibility and applies the fixed 100% scheme discount to eligible service charges.
  • Save the bill with an optional remark. The bill number looks like BILL-YYYYMMDD- plus a random code.
  • Record a full or partial payment by Cash or GPay. GPay asks for a confirmation that the payment was received. A zero-payable bill does not take a payment.
  • Bill status is Open, Partial, Paid, or Waived.
  • Open the receipt, print it, and add a later payment against the balance.
  • An administrator can reverse a confirmed payment. The reversal stores who reversed it, when, and why. The bill balance is recalculated.
  • Repeating the same bill or payment request with the same request key returns the original result instead of creating a second charge.
  • Billing reports cover a day, week, month, or a custom range of up to 366 days. They show service charges, discounts, net payable, Cash and GPay collections, reversals, outstanding balance, and breakdowns by service, scheme, and staff. A billing user sees only their own bills. An administrator can include every billing user or one selected user.

9. Rules the server already enforces

  • A scheme discount and a billing discount are calculated from stored scheme and tariff rows.
  • An inactive patient or an inactive department cannot receive a new OP visit.
  • An inactive scheme cannot be assigned, and an assigned scheme that fails gender or age eligibility is rejected.
  • Primary and alternate phone numbers cannot be the same.
  • A bill cannot be paid above the outstanding balance.
  • A saved bill keeps the service name, tariff, and scheme details from the moment it was created.
  • A saved OP visit keeps the fee, discount, and scheme details from the moment it was created.

10. Present limits of the implementation

These items are outside the current software, or are only partly built:

  • No doctor, consultation, prescription, inpatient, ward, bed, pharmacy, laboratory, or inventory screens.
  • No live statistics on the admin home page. Those three cards are placeholders.
  • OP payment is stored on the visit. It does not have a separate payment reversal screen. Billing payments do.
  • The project does not include a backup or restore program. Database backup remains an operating-system task.
  • Patient documents and file uploads are not implemented.
  • Automated tests exist for billing calculations, scheme eligibility, and the billing catalog importer. The rest of the application is exercised through the screens and API.
